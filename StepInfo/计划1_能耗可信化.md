# 计划 1 —— 让单家庭日模拟的能耗结果可信、可读、可验证

> 依据：`StepInfo/00_需求与规则.md`（已重读）。本步**不改动任何外部文件夹**，只在 LLMWorld 内工作。

## 为什么做这步（动机）

后续一切实验（政策、事件、人口级模拟、实证对齐）都建立在"每天模拟产生的能耗数据可信"之上。当前存在三个会污染所有下游结果的问题：

1. **常开电器（冰箱等 always_on）的耗电完全丢失**：第四层决策明确要求 LLM 跳过 always_on，能耗计算只遍历 LLM 决策 → 冰箱 24h 基载从不计入总用电 → 日用电量系统性偏低（约 1.2kWh/天/冰箱，一个家庭少算 20%+）。
2. **没有家庭级分钟负荷曲线**：论文核心产出（RQ1 "分钟分辨率负荷"）缺失，只有"每电器分段"输出，无法画负荷曲线、无法与真实数据对比。
3. **LLM 输出无校验 + 失败被静默吞掉**：非法 unique_id/action 直接跳过、json 解析失败裸 except → 结果不可信且无感知。
4. **并发无上限**：违反用户"同时不超过 10 个"的硬性要求（现为一 prompt 一线程，成员多时可能 >10）。

## 怎么做（方法）

- 先读 `worlds/495/3168/house_0001/household.json` 了解真实家庭数据结构，测试用它构造 Home
- utils.py 从 planner/executor 现有实现中抽取（保持输出格式与日志格式不变，减少回归风险）
- energy_calculator 增加基载：遍历 `home.appliance_registry` 中 `appliance_type == "always_on"` 的电器，`daily_energy_kwh/24/60` 每千瓦时叠加到分钟数组
- 校验逻辑：决策中的 `unique_id` 必须在 registry；`action` 必须在 `appliance.get_available_actions()`；违规则记录 warning + 跳过该操作
- subagent：`ThreadPoolExecutor(max_workers=10)`，每任务重试 3 次（等待 2^n 秒），超时 120s，最终失败抛 `LLMCallError`

## 怎么验证

1. `python Implement/test_offline.py` 全绿（本地无 API）
2. 用 worlds/495 的 household.json 构造 Home → 喂一段合成决策（含合法/非法 unique_id）→ 运行 EnergyCalculator → 检查：冰箱基载 1.2kWh 在总用电里、分钟曲线 1440 点、非法项出现在 warnings
3. `git status` 确认只动 LLMWorld 内文件 → git 提交

## 涉及论文想法（学术依据）

- Richardson et al. (2010) 一分钟分辨率需求建模：以分钟级为单位聚合负荷，是本研究对齐的基准粒度 → 本步的 1440 点曲线即为该思想的实现落地。
- 校验/失败显式化借鉴 SALM (Koley 2025) 中"结构化数据保证可验证性"的工程思想：不可信输入绝不允许静默进入统计。
